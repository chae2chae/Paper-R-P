how-to-skills

TL;DR

TypeScript 거장 Matt Pocock이 18개월간 AI 에이전트로 개발하며 정리한 스킬 모음. GSD/BMAD/Spec-Kit이 프로세스 전체를 장악하는 것과 달리, 작고 조합 가능한 단위로 만들어 어떤 모델·에이전트에서도 동작. 핵심 명제는 "Code is not cheap. Bad code is the most expensive it's ever been." — AI가 코딩 속도를 가속하는 만큼 소프트웨어 엔트로피도 가속되므로, DDD/TDD/Deep Modules 같은 수십 년 된 펀더멘털이 더 중요해졌다는 것.

GitHub: 49.2k stars, 4k forks.

1. 왜 이 스킬들이 존재하는가 — 6가지 함정

Pocock의 41만뷰 발표 "Software Fundamentals Matter More Than Ever" (2026.4) 기준 분류.

함정 #1 — AI가 의도와 다른 걸 만든다

"No one knows exactly what they want." — The Pragmatic Programmer

너와 에이전트 사이의 communication gap. 에이전트는 보통 프로젝트에 던져져서 jargon을 추측으로 메우고 시작함. 해결: grilling 세션 — 에이전트가 너에게 detailed question을 던지게 만들어서 의도를 강제로 명확화.

→ /grill-me, /grill-with-docs

함정 #2 — 모호한 PRD

요구사항이 코드로 번역되는 순간 무너짐. 에이전트와 도메인 전문가(=너)가 다른 언어로 말하고 있기 때문. 해결: ubiquitous language (DDD) — 공유 언어 문서를 만들어 jargon을 디코딩.

예시:

  • BEFORE: "There's a problem when a lesson inside a section of a course is made 'real' (i.e. given a spot in the file system)"
  • AFTER: "There's a problem with the materialization cascade"

CONTEXT.md에 도메인 용어 정의 → 변수/함수/파일명 일관성 확보 → 에이전트가 thinking 토큰 절약. Pocock이 "이 레포에서 가장 강력한 기법"이라고 한 부분.

→ /grill-with-docs (CONTEXT.md/ADR 인라인 갱신), /to-prd

함정 #3 — 코드 리뷰의 죽음

"The rate of feedback is your speed limit." — The Pragmatic Programmer

AI 시대에 코드 리뷰는 사실상 죽었음. 사람이 따라잡을 속도가 안 됨. 해결: 피드백 루프를 자동화 — static types, 브라우저 접근, 자동 테스트, 그리고 무엇보다 red-green-refactor 사이클. 에이전트가 실패 테스트를 먼저 쓰고 그걸 통과시키게 하면 일관된 피드백 → 훨씬 나은 코드.

→ /tdd (red-green-refactor 강제), /diagnose (디버깅 루프)

함정 #4 — Deep vs Shallow Modules

"The best modules are deep. They allow a lot of functionality to be accessed through a simple interface." — John Ousterhout, A Philosophy of Software Design

이게 이 스킬셋 전체의 핵심 설계 철학.

  • Deep module: 인터페이스는 단순, 내부에 많은 기능 숨김. 좋은 추상화. 예) 파일시스템 open/read/write/close
  • Shallow module: 인터페이스가 내부 구현만큼 복잡. 추상화 이득 없이 비용만 있음

AI 시대에 왜 치명적인가: 에이전트는 빠르게 코드를 양산함 → shallow module을 마구 찍어냄 → 인터페이스 폭발 → 컨텍스트 폭증 → 에이전트 자체가 자기 코드베이스에서 길을 잃음.

해결은 deepening — shallow를 deep으로 리팩토링. /improve-codebase-architecture README에 "find deepening opportunities"라고 명시된 게 이 의미. Ousterhout 용어를 정확히 차용함.

→ /improve-codebase-architecture (deepening 작업), /zoom-out (상위 관점 강제)

함정 #5 — 의존성 관리

에이전트는 패키지를 거리낌 없이 추가함. 의존성 그래프가 통제 안 되면 코드베이스가 빠르게 부패. 해결: 의존성 결정을 ADR로 문서화해서 추가 시 challenge 가능하게.

→ /grill-with-docs (ADR 생성/유지), /improve-codebase-architecture

함정 #6 — 설계 부재

"Invest in the design of the system every day." — Kent Beck, Extreme Programming Explained

에이전트에게 코딩만 시키고 설계는 안 시키면 entropy 가속. 해결: 설계를 일상 작업으로 통합 — 모든 변경 전에 모듈 영향 검토, 주기적으로 architecture 정리.

→ 모든 스킬에 녹아있음. 특히 /improve-codebase-architecture 주기적 실행(며칠에 한 번 권장), /to-prd(어떤 모듈 건드리는지 사전 검토), /zoom-out

3. 설치 방법 (30초 셋업)

npx skills@latest add mattpocock/skills

순서:

  1. 위 명령어 실행
  2. 원하는 스킬 + 설치할 에이전트(Claude Code, Codex 등) 선택. 반드시 /setup-matt-pocock-skills 포함
  3. 설치 방식 선택:
    • Symlink (Recommended): 베이스라인 한 곳(~/.skills/...)에 실제 파일, 각 에이전트 디렉토리는 심링크. npx skills@latest 재실행 시 한 곳만 갱신해도 전체 반영
    • Copy: 각 에이전트 디렉토리에 독립 사본. 에이전트별 커스텀 가능, drift 위험
  4. 에이전트에서 /setup-matt-pocock-skills 실행 → 다음 항목 물어봄:
    • 이슈 트래커 (GitHub / Linear / 로컬 파일)
    • triage 시 사용할 라벨
    • docs 저장 위치
  5. 끝.

7. 비판적 평가

객관적으로 짚어둘 것:

  1. 49.2k stars지만 검증 기간 짧음. 2026년 작성, 장기 프로덕션 데이터 부재. 인기 ≠ 효과.
  2. "any model에서 작동"은 마케팅. 실제로 Claude Code/Codex 등 agentic 환경 전제. 일반 ChatGPT/Cursor엔 그대로 안 맞음.
  3. /caveman 75% 토큰 절감은 측정 방법론 공개 없음. 응답 품질 trade-off 가능성.
  4. "새로운 발명"이 아니라 "재포장". DDD ubiquitous language, Ousterhout deep modules, Beck XP, Pragmatic Programmer — 전부 검증된 고전. 가치는 LLM 컨텍스트로의 이식 자체에 있음.
  5. 레포 본질은 마크다운 프롬프트 + 셋업 스크립트(100% Shell). Pocock 본인이 "Hack around with them. Make them your own"이라 명시 — 통째로 쓰기보다 읽고 본인 스타일로 수정하는 게 정석.
  6. Deep Module 개념은 적용 난이도가 높음. "shallow를 deep으로 리팩토링"은 인간도 잘 못하는 일. 에이전트가 /improve-codebase-architecture 한 번 돌렸다고 진짜 deepening 됐는지 검증할 메커니즘이 README에 명확하지 않음. 결과물 신뢰는 사용자 판단 영역.

한 줄 평

소프트웨어 엔지니어링 펀더멘털을 LLM 에이전트용 프롬프트 스킬로 패키징한 것. 핵심은 "AI는 좋은 코드베이스에서만 빛난다"는 인식 + Ousterhout의 Deep Module 철학을 에이전트 워크플로우에 강제 주입한 것. /grill-with-docs(ubiquitous language) + /improve-codebase-architecture(deepening) 두 개만 도입해도 가치 충분.

검증해볼 만한 질문: CONTEXT.md 기반 ubiquitous language가 실제로 토큰 사용량과 코드 품질에 측정 가능한 영향을 주는가? Deep Module deepening이 에이전트 자가 평가만으로 신뢰 가능한가? 정량 데이터가 공개되면 훨씬 설득력 있을 것.
