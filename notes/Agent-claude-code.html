LLM wiki의 아이디어

문서를 그냥 질의 시점에 검색하는 게 아니라, 새 소스가 들어올 때마다 LLM이 그 내용을 기존 위키에 통합한다. 예를 들면:

  • 새 문서를 읽고
  • 핵심 내용을 뽑고
  • 기존 주제 페이지를 수정하고
  • 관련 엔티티 페이지를 업데이트하고
  • 이전 주장과 충돌하면 그 모순도 표시하고
  • 교차 링크까지 정리하는 식이야. 즉 지식이 질문마다 재생성되는 게 아니라, 한 번 정리되어 계속 누적되는 중간 산출물(wiki)이 생김

“raw documents → LLM-maintained wiki → user query”

즉 사용자는 원문만 들고 직접 정리하지 않고, LLM이 그 사이에서 구조화된 마크다운 위키를 계속 유지보수하는 역할을 맡는다. 사용자는 소스를 넣고 질문하고 방향을 잡고, LLM은 요약, 분류, 링크 연결, 페이지 수정, 기록 유지 같은 “잡무”를 담당하는 구

구조
  • Raw sources 논문, 기사, 이미지, 데이터 같은 원본 자료. 수정하지 않는 source of truth.
  • The wiki LLM이 만드는 마크다운 페이지 모음. 요약, 개념 페이지, 엔티티 페이지, 비교 페이지 등.
  • The schema AGENTS.md, CLAUDE.md 같은 운영 규칙 문서. 위키를 어떤 구조로 만들고, 새 자료를 받으면 어떻게 반영하고, 질문에 어떻게 답할지 정하는 규칙.
운영방식
  • Ingest: 새 자료를 넣으면 LLM이 읽고 위키 여러 페이지를 갱신
  • Query: 질문에 답할 때 위키를 읽고 합성해서 답변
  • Lint: 위키가 커지면 모순, 고아 페이지, stale claim, 빠진 링크 같은 걸 점

LLM이 지식 저장소의 편집자 + 사서 + 유지보수자 역할을 하는 패턴 => 노트와 지식의 재사용이 가능한 구조 그리고 그 재사용이 단순히 거기서 검색하는 것이 아니라 애초에 한번 정제된 데이터가 있고, 거기에서 query 가능하게

LLM wiki vs My LLM wiki

  • 어떻게 사용하는가? HOWTO

Karpathy 원문은 "패턴"이고, 내 wiki(07_LLM_WIKI)는 그걸 VLA 연구 도메인에 맞춰 구체화한 "구현체"다. 원문은 의도적으로 추상적 — "LLM이 maintain하는 markdown wiki"라는 아이디어만 전달. 내 wiki는 Obsidian 볼트 + VLA 연구용으로 규칙을 박아놓은 버전.

1. 구조의 구체화 정도

항목Karpathy 원문My wiki
디렉토리3 layer (raw/wiki/schema) — 추상_meta/, _schema/, entities/, concepts/, sources/, analyses/, raw/, overview.md — 고정
페이지 유형예시만 (entity, concept, summary, comparison)Entity-, Concept-, Source-, Analysis- prefix 강제
Frontmatter언급 없음 (Dataview 얘기 정도)YAML frontmatter 필수 (type, sources, updated 등)
링크 규칙"cross-references가 생긴다" 정도페이지당 최소 2개 [[]] 링크 강제

2. Obsidian 볼트 통합 (내가 추가한 것)

Karpathy 원문은 wiki를 독립 리포로 가정. 나는 01_Research/, 02_Papers/, 03_Ideas/, 05_Archive/를 읽기 전용 raw source로 편입시키고 07_LLM_WIKI/raw/는 "기존 폴더에 없는 것만"으로 분리. 기존 Zotero + 연구 볼트 자산을 재활용하려는 현실적 설계.

3. _meta/context.json (내 고유 레이어)

Karpathy 버전엔 없음. 원문은 index.md + log.md 두 개뿐. 나는 세션 간 연속성을 위해 context.json을 추가해서 wiki_stats, ingested_sources, pending_sources, open_questions, session_log, bootstrap_prompt까지 상태로 박아놓음 — 세션 시작/종료 시 읽고 쓰는 프로토콜을 schema에 명문화.

4. 모순 처리 방식

원문은 "contradictions를 flag한다"고만 서술. 나는 > [!warning] 모순 Obsidian callout 포맷으로 구체화.

5. 도메인 고정 vs 범용

원문은 personal/research/book/business 등 여러 예시를 나열. 내 wiki는 VLA 아키텍처·Online RL·Sim2Real·일반화 실패로 도메인이 고정되어 있고, overview.md에 도메인별 프레임 다이어그램까지 박아둠.

한 줄 요약

  • Karpathy: "LLM이 유지하는 markdown wiki" — idea file.
  • My wiki: 그걸 Obsidian + VLA 연구 + 세션 상태 관리까지 얹은 실제 운영 시스템.

원문 대비 더 엄격한 쪽으로 간 부분 — 링크 최소 2개 강제, frontmatter 필수, 파일명 prefix, context.json 상태 파일. 원문 대비 덜 챙긴 부분 — Marp 슬라이드·차트 같은 출력 형식 다양화, qmd 같은 검색 CLI는 아직 미도입 (index.md 기반).
