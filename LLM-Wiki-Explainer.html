01

왜 위키인가 — RAG와 뭐가 다른가

LLM에 문서를 그냥 넣으면 RAG가 작동한다. 질문이 올 때마다 관련 조각을 찾아 답을 만든다. 편하지만 지식이 쌓이지 않는다. 매 질문마다 처음부터 다시 조합할 뿐이다.

"위키의 아이디어는 이렇다 — 질의 시점에 검색하지 말고, 새 소스가 들어올 때마다 LLM이 기존 위키에 통합해둬라. 요약하고, 기존 주제 페이지를 수정하고, 엔티티 페이지를 갱신하고, 이전 주장과 충돌하면 모순을 표시한다."
RAG

질의 시점에 재조합

원문 청크 저장 → 임베딩 검색 → 매번 답 생성. 지식이 누적되지 않고, 모순도 안 잡힌다.

LLM Wiki

한 번 정제된 중간 산출물

새 소스 입력 즉시 wiki에 통합. 요약/링크/모순 플래그/인덱스까지 유지. 사용자는 정리된 knowledge base에 질의한다.

02

3-Layer 패턴 (Karpathy 원문)

원문은 세 레이어로 구성된다 — Raw sources, The wiki, The schema. LLM은 이 사이에서 편집·유지보수 작업을 맡는다.

3-Layer 구조

사용자는 원문을 넣고 질문만 한다. LLM이 사이에서 wiki를 계속 갱신.

03

데이터 흐름 — Ingest · Query · Lint

wiki를 실제로 운영하는 세 가지 동작. 하나하나가 LLM에게 위임되는 일감이다.

01 · INGEST

소스 넣기 → 여러 페이지 갱신

새 논문/기사 진입 시 요약 페이지 생성, entity·concept 갱신, 모순 체크, index/log 업데이트까지 한 번에.

"이 논문 ingest 해줘"
02 · QUERY

질문 → wiki 합성 답변

관련 페이지를 읽고 합성. 보존 가치 있는 답변은 analyses/에 새 페이지로 저장해 재사용.

"VLA에 adaptive chunking이랑 residual RL 어떻게 붙이지?"
03 · LINT

주기 점검 → 리포트

고아 페이지, stale 주장, 모순 callout, 끊긴 링크, index 불일치를 한꺼번에 찾아 리포트.

"wiki 점검해줘"

05

Karpathy 원문 vs 내 구현

Karpathy 원문은 "패턴"이고 내 wiki는 그걸 VLA 도메인에 맞춘 "구현체". 원문 대비 더 엄격한 쪽으로 간 부분이 많다.

07

운영 루틴

사용자(나)와 LLM의 역할이 분리돼 있다. 나는 방향과 질문을 주고, LLM은 요약·링크·페이지 수정·모순 플래그·인덱스 유지를 맡는다.

01 · INGEST

소스 넣기

새 논문 → "이거 ingest 해줘" → 요약·개념·엔티티·모순 한 번에 갱신.

02 · QUERY

질문하기

LLM이 wiki 합성 답변. 보존 가치 있으면 analyses/로.

03 · LINT

점검하기

주기적으로 "wiki 점검해줘" → 고아·모순·stale 리포트.

04 · STEER

방향 잡기

overview.md의 열린 질문 갱신 → 다음 ingest 후보 결정.

08

가져갈 만한 것 · Takeaways

다른 도메인·다른 툴을 쓰더라도 적용가능한 설계 결정들.

  • 도메인을 고정하라. 범용 wiki는 관리 비용이 폭발한다. "VLA 연구"처럼 좁은 도메인에 스키마를 박아두면 LLM 출력이 훨씬 안정된다.
  • 파일명 prefix로 타입을 강제. Entity-, Concept-, Source-, Analysis-. LLM이 실수로 category를 섞는 일이 없어진다.
  • 세션 연속성용 상태 파일(context.json)을 둬라. index.md + log.md만으로는 다음 세션이 맥락을 복원하기 어렵다. 구조화된 JSON 하나가 훨씬 안정적.
  • RAG가 아니라 "LLM이 유지하는 중간 산출물"로 생각하라. 매 질문마다 재조합 ✗, 한 번 정제된 knowledge base에 질의 ✓.
  • 기존 폴더를 raw source로 편입. Zotero·연구 폴더를 복사하지 말고 읽기 전용 참조로만 써라. 중복·동기화 지옥을 피한다.
  • 모순은 flag가 아니라 callout으로. Obsidian > [!warning] 같은 시각적 블록이 있으면 나중에 리뷰가 쉽다.
